Secret base setup routines -- scope, Ruby, verified 2026-09-02
======================================================================

STATUS: FINISHED. A-E are all done, and so are the Secret Power entry
script and the decoration PC. See "PROGRESS" and then "FINISHED" at the
end. The history below is kept because it explains why the work went in
this order -- the five "missing secret base specials" were never the
blocker, and porting them first would have been wasted work.

HEADLINE

The engine never loads the real secret base maps. Game3.makeSecretBaseMap()
(src/core/Game3.lua) synthesises a hand-written 7x6 empty box with one
PC tile and no scripts:

    local w, h = 7, 6
    ... wall ring, one MB_SECRET_BASE_PC tile ...
    id = Game3.SECRET_BASE_MAP_ID   -- "secret_base", a pseudo-map

The ROM's 24 real interiors (g25_0 .. g25_23) are extracted into the
cache and never entered. Every one of the five "missing" specials lives
in those maps' scripts. So they are unreachable not because of a
missing handler but because the maps that call them never load.

Implementing the five handlers against today's architecture would add
five functions that can never run.

WHAT THE FIVE ROUTINES ACTUALLY ARE

Note: misc/unfinished_features_audit.txt names these one ordinal off
(it counted the `.macro def_special` definition line as an entry). The
ids below were re-derived from data/specials.inc via the oracle's own
names.py and cross-checked against tools/gba_oracle/check_specials.py,
which reports 0 off-table against the engine's existing 325 constants.

  id  real name      what it does (secret_base.c)
  --  -------------  ---------------------------------------------
  16  sub_80BCE1C    sub_810FB10(1) + CreateSecretBaseEnemyParty():
                     builds the base owner's party to battle.
  17  sub_80BCE90    daily reset of battledOwnerToday across all 20
                     base records (gated on FLAG_DAILY 0x8C2), then
                     0x8004 = GetSecretBaseOwnerType(cur),
                     RESULT = battledOwnerToday.
  18  sub_80BBDD0    walks the 16-slot decoration array (or the 12-slot
                     playerRoomDecor when not in a base), and for each
                     DECORPERM_SOLID_MAT entry claims a free object
                     slot (flagId 0xAE + n), sets VAR_OBJ_GFX_ID_n to

  24  sub_80BBC78    FadeScreen + task: warps the player to the entry
                     coords for this layout, from gUnknown_083D1374.
  25  sub_80BCE4C    one line: secretBases[cur].battledOwnerToday = RESULT.

WHERE THEY SIT (g25_0, representative of all 24)

  mapScripts.onWarp     -> id 18   (runs on every entry)
  mapScripts.onFrame    -> id 24   (the "Want to make your SECRET BASE
                                    here?" yes-branch, i.e. creation)
  objects[1] script     -> id 17, id 25 x20, id 16

objects[1] is the base owner: localId 1, graphicsId 255 (GFX_VAR_F, set
by special 22 SetSecretBaseOwnerGfxId, already implemented), hidden
behind flagId 173. objects[2..15] are the 14 decoration sprite slots,
graphicsId 240-254 (GFX_VAR_0..E), flagIds 174-187 -- and onTransition
sets all fourteen unconditionally, i.e. every decoration slot starts
hidden and id 18 is what selectively un-hides them.

REACHABILITY IN A LINK-LESS PORT

  id 24  REACHABLE and on the critical path -- it is the base-creation
         confirm step for your own base.
  id 18  REACHABLE twice over: the base interior, and (via its
         !CurrentMapIsSecretBase branch) the player's BEDROOM
         decorations in Littleroot. 26 call sites = 24 bases + 2
         bedrooms. With no placement data it is a legitimate no-op.
  id 16  }
  id 17  } NOT REACHABLE. All three are the base-owner interaction.
  id 25  } A second base record only ever arrives through record
         mixing / link cable, which this port cannot have, and the
         owner object stays hidden behind flag 173. Porting them is
         cheap (17 and 25 are ~3 lines each) but has zero observable
         effect.

TWO DIVERGENCES THAT WILL BITE

1. VAR_CURRENT_SECRET_BASE semantics are wrong today.
   ROM: it is an INDEX into gSaveBlock1.secretBases[20]; the layout is
   a separate field on the record --
       gCurrentSecretBaseId = secretBases[VarGet(VAR_CURRENT_SECRET_BASE)].secretBaseId
   Engine: Game3:setCurrentSecretBaseVar() writes self.secretBase.id,
   which is the LAYOUT id taken from the BG event (bg.secretBaseId).
   The two only coincide at 0. Every one of the five routines indexes
   secretBases[VarGet(VAR_CURRENT_SECRET_BASE)], so this must be fixed
   before any of them are ported literally. With no record mixing the
   index is always 0; store the layout id separately.

2. self.secretBase carries only { id, mapId, x, y, outX, outY }.
   The ROM record (struct SecretBaseRecord, include/global.h:154) also
   has decorations[16], decorationPos[16], battledOwnerToday, gender,
   registryStatus, toRegister, playerName, trainerId, numTimesEntered
   and the owner party. self.decorations is a flat owned-count
   inventory only (self.decorations[id] = count) -- no placement data
   anywhere, matching misc/decoration_system_research.txt.

SUGGESTED ORDER

  A. Load the real interior. Replace makeSecretBaseMap() with the real
     g25_<layout> map. gUnknown_083D1374 gives the mapping for free:
     25 rows of { mapNum, 0, x, y } indexed 4 * (secretBaseId / 10) --
     a ~100-byte table, findable by its mapNum run, extracted the same
     way the door table was. This alone makes the ROM scripts run and
     is what turns 18/24 from dead code into needed code.
     Medium effort, high confidence, visually verifiable.

  B. Widen the save record (decorations/decorationPos at minimum) and
     fix the VAR_CURRENT_SECRET_BASE semantics per divergence 1.
     Small, mechanical, worth doing even alone -- it is a correctness
     fix today.

  C. id 24. Needs only the table from A. Small, self-contained,
     verifiable headlessly the way the door frames were.

  D. id 18. Needs B plus the decoration catalog's tiles pointer (the
     121-entry catalog is already verified byte-for-byte in
     misc/decoration_catalog_verified.txt; the tile-graphics pointer at
     +0x1c is the one field never extracted). Observable only once
     something can actually place a decoration.

  E. ids 16 / 17 / 25. Port for completeness whenever; they cannot be
     exercised. 16 additionally needs CreateSecretBaseEnemyParty, which
     has no data source without a second base record.

FINISHED -- 2026-09-02
======================================================================

Everything below was the remaining gap. All of it is now in, and all
five Ruby suites pass (ruby_battle grew from 5407 to 5499 checks).

1. THE SECRET POWER ENTRY SCRIPT was the engine's own invention, and is
   now the ROM's. useSecretPower() used to be four hand-written lines
   ("Used SECRET POWER!", "Move your SECRET BASE here?") with no
   entrance-type distinction at all. It now follows gUnknown_081A2C51:

     special sub_80BB70C (id 21, which was never even dispatched) reads
     the metatile behaviour in front of the player into VAR_0x8007 --
     1 red cave, 2 brown, 3 blue, 4 yellow, 5 either tree, 6 shrub,
     0 nothing. Caves take one branch, the tree and the shrub their own.

     Each branch has its own three strings, all from the cart:
       cave   "There's a small indent in the wall." /
              "...Use the SECRET POWER?" / "Discovered a small cavern!"
       tree   "If some vines drop down, this tree can be climbed." /
              "...Use the SECRET POWER?" / "A thick vine dropped down!"
       shrub  "If this clump of grass can be moved, it might be possible
              to go inside." / "...Use the SECRET POWER?" /
              "Discovered a small entrance!"
     With nobody who knows the move it is EventScript_1A2EF7 -- the sign
     line alone, no prompt. With the move it is msgbox MSGBOX_YESNO, then
     UsedCutRockSmashText ("{MON} used SECRET POWER."), then the field
     effect, then the discovery line, then EventScript_1A2DB8.

     FLDEFF_USE_SECRET_POWER_CAVE (11) / _TREE (26) / _SHRUB (27) are
     new, wired through the same dofieldeffect+waitstate path Cut and
     Rock Smash already used. Each plays its own SE (SE_M_ROCK_THROW,
     SE_M_SCRATCH, SE_M_POISON_POWDER) and opens the entrance metatile
     partway through its 40 frames -- the caves and the shrub at 20, the
     tree only at 40, as the sprite callbacks do.

     AskToMoveSecretBase is three msgbox MSGBOX_YESNO gates in a row
     ("You may only make one SECRET BASE...", then the decorations
     warning, then "Moving completed. Would you like to use the SECRET
     POWER?"), not one prompt.

2. THE ENTRANCE METATILES. gUnknown_083D1358 (ROM 0x083D1358, the 0x1C
   bytes immediately before the entry table -- read off the cart and
   matched byte-for-byte) is seven { closed, open } pairs.
   SetOpenedSecretBaseMetatile swaps either way, sub_80BC474 only closes.
   MoveSecretBase turns out to be sub_80BC474 + IncrementGameStat +
   ResetSecretBase(0): it WIPES the record, and the new one is written
   afterwards by EventScript_1A2DB8. The engine's special 330 was only
   the game stat.

   SetOccupiedSecretBaseEntranceMetatiles runs on map load. The ROM only
   has to OPEN the owned one because the layout comes back fresh from
   the cart each time; this engine hands out one shared cached table per
   map, so it sets every entrance on the map explicitly -- open if it is
   yours, closed otherwise -- which self-corrects the cached grid.

4. STAMPING. gUnknown_083EC97C and gUnknown_083EC984 -- the two tables
   this file used to say still needed extracting -- are eight bytes each
   at ROM 0x083EC97C / 0x083EC984, verified against the cart. They are
   per-cell elevation nibbles for DECOR_STAND (38) and DECOR_SLIDE (34)
   ONLY; sub_80FF1B0 returns 0xFFFF for everything else, meaning "leave
   the cell's elevation alone". Both decorations are 8 cells.
   sub_80FF1EC / sub_80FF394 / InitSecretBaseAppearance are ported.

   One divergence worth knowing: the ROM re-reads the map layout from
   the cart on every load, so its stamps always land on a clean grid.
   This engine shares one cached table per map, so a pristine copy is
   snapshotted before the first write and restored before each stamping
   pass. Without that a decoration would double-stamp on re-entry and
   survive being put away.

5. THE DECORATION PC (special 14) is no longer a no-op.
   DECORATE / PUT AWAY / TOSS / EXIT with gUnknown_083EC624's per-option
   description following the cursor, then the eight categories, then the
   items. DECORATE opens a placing-decoration avatar mode: the map stays
   live, arrows steer a footprint cursor anchored on its bottom-left cell
   (tinted by whether sub_80FFC24 accepts the spot), A offers "Place it
   here?" and B "Cancel decorating?". Committing is sub_8100174 -- first
   free room slot, id plus packed x/y -- then either sub_80FF394's stamp
   or, for a DECORPERM_SOLID_MAT one, sub_80BBDD0's object-event path.
   PUT AWAY clears a room slot and rebuilds the room; TOSS clears the
   inventory slot and re-sorts.
   The three refusals are the ROM's: "This is in use already."
   (sub_80FEFA4), "This decoration can't be placed in your own room."
   (the bedroom takes only DOLLs and CUSHIONs), and "No more decorations
   can be placed. The most that can be placed is 16." (sub_80FF58C,
   counting the ROOM's slots -- not the inventory's).

6. THE PC TILE ITSELF was routed to box storage. Game3.isPc treated
   MB_SECRET_BASE_PC (0xB0) as a Pokemon storage PC, so pressing A on the
   base's PC opened WITHDRAW / DEPOSIT / MOVE / SEE YA and special 14
   never ran. metatile_behavior.c MetatileBehavior_IsPC is MB_PC (0x83)
   and NOTHING else; 0xB0 is a separate branch further down
   GetInteractedMetatileScript.

   That same branch is gated on the player standing at the tile's own
   elevation and covers four behaviours, none of which were dispatched:
     0xB0 MB_SECRET_BASE_PC               SecretBase_EventScript_PC
     0xB1 MB_RECORD_MIXING_SECRET_BASE_PC SecretBase_EventScript_
                                          RecordMixingPC
     0xBF MB_SECRET_BASE_SAND_ORNAMENT    dofieldeffect FLDEFF_SAND_PILLAR
     0xC4 MB_SECRET_BASE_SHIELD_OR_TOY_TV SecretBase_EventScript_
                                          ShieldOrToyTV
   All four are wired now. Note the last one is what CALLS special 307 --
   until this existed, 307 was correct but unreachable.

   SecretBase_EventScript_PC is playse SE_PC_LOGIN, "{PLAYER} booted up
   the PC.", the turn-on field effect behind a waitstate, waitbuttonpress,
   SE_SELECT, then multichoice 5 (DECORATION / PACK UP / CANCEL) or 6
   (with REGISTRY) depending on FLAG_SECRET_BASE_REGISTRY_ENABLED. PACK UP
   is the decorations warning then MoveOutOfSecretBase; the decoration
   PC's EXIT returns here rather than closing, per
   gpu_pal_decompress_alloc_tag_and_upload's
   ScriptContext_SetupScript(SecretBase_EventScript_PCCancel).

7. DECORATION NAMES. gDecorations[].name is an INLINE u8[16] at +0x01, not
   a pointer -- only the description at +0x18 is one. The first extraction
   skipped both as "text pointers", so 99 of the 121 decorations had no
   name and the PC listed them as "DECOR 43". Both are extracted now for
   all 121 rows and the PC prints the description under the highlighted
   entry, per sub_80FE7A8. Cache contract ruby50 -> ruby51.

8. DECORATIONS WITH EFFECTS. Several decorations react when you walk on
   them, through two separate ROM mechanisms, neither of which was here.

   SecretBase_OnResume is `setstepcallback 6`, i.e. field_tasks.c's
   gUnknown_08376364[6] = sub_80BCF1C. It fires only on the frame the
   player's tile CHANGES, and picks exactly one of four:
     0xBA GLITTER MAT     a 32-frame sparkle, SE_M_HEAL_BELL at frame 8
     0xB8 BALLOON         metatile +1/+2/+3 every 7 frames, the pop SE on
                          the +2 step -- 824 red, 828 blue, 832 yellow,
                          552 mud (DoBalloonSoundEffect)
     0xBE BREAKABLE DOOR  facing south it shatters at once; walking north
                          into it waits 7 frames. Either way SE_BREAKABLE_
                          DOOR and metatiles 630 (lower) / 622 (upper)
     0xBD MUSIC NOTE MAT  the note is chosen by metatile -- 632..638 are
                          C D E F G A B and 691 is high C -- 7 frames after
                          the step
   The jump and spin mats are NOT that callback; they are forced movement,
   listed in field_player_avatar.c's sForcedMovementTestFuncs next to ice
   and the currents:
     0xBB JUMP MAT        ForcedMovement_SecretBaseJumpMat -- jump in
                          place, SE_LEDGE, you do not change tile
     0xBC SPIN MAT        ForcedMovement_SecretBaseSpinMat -- SE_WARP_IN
                          then the facing cycles W, E, N, S
   The sand ornament (0xBF) and the shield / toy TV (0xC4) are interaction
   scripts rather than step effects and went in with item 6 above.

9. TWO RELOAD BUGS, both found from the player's own save.

   Placed decorations vanished on CONTINUE while the record still listed
   them as in use. enterMap stamps them in, but applySave then calls
   setMapLayoutIndex for the saved mapLayoutId, and that rewrites the
   whole grid from the layout table -- wiping every stamp. The ROM has the
   opposite order: InitMapLayoutData lays the layout down and
   InitSecretBaseAppearance bakes the decorations on top of it. Fixed by
   re-baking at the end of setMapLayoutIndex, which is correct for any
   caller since a layout swap always clears the grid.

   The DECORPERM_SOLID_MAT decorations (dolls and cushions) stayed hidden
   after any load that did not walk in through the entrance. They are
   object events, not grid tiles, so InitSecretBaseAppearance skips them
   and sub_80BBDD0 has to run -- and that is gated behind
   SecretBase_OnWarp's `map_script_2 VAR_SECRET_BASE_INITIALIZED, 0`,
   which gUnknown_081A2E14 arms by zeroing the var on the way in. A save
   loaded while already inside never runs that script, so the gate stayed
   shut. enterMap now zeroes the var for any entry into a base, the same
   way it already sets FLAG_DECORATION_1 for the same reason.

10. THE MAT LATCH. The first cut of the jump and spin mats re-fired every
   frame you stood on them, which softlocked the player. The ROM's guard
   is in GetForcedMovementByMetatileBehavior: it refuses to test ANY of
   sForcedMovementTestFuncs while PLAYER_AVATAR_FLAG_5 (1 << 5, the
   `unk1 |= 0x20` in the decomp) is set, and
   PlayerAvatar_DoSecretBaseMatJump sets that flag when it finishes.
   PlayerAllowForcedMovementIfMovingSameDirection clears it again once
   runningState == MOVING, i.e. after you actually walk off.

   Both mats are also multi-beat tasks, not one-shot calls:
     JUMP  two jump-in-place actions (data[1] stops it once > 1), each
           with SE_LEDGE, then preventStep off and the latch on. You stay
           on the tile.
     SPIN  SE_WARP_IN and the controls lock, then the facing turns one
           beat at a time. Step1's direction table is indexed by
           movementDirection, giving SOUTH->WEST, WEST->NORTH,
           NORTH->EAST, EAST->SOUTH -- counter-clockwise. It ends at
           Step3 with GetWalkSlowMovementAction(GetOppositeDirection(the
           direction you arrived facing)), so the spin mat always walks
           you back off the way you came. That is why it needs no latch.
   The first cut had the spin order wrong (west->east) as well.

11. DOLL AND CUSHION SPRITES were never extracted. extractSprites only
   renders the graphics ids collectGraphicsIds finds, and that scanned
   map object events -- but a DECORPERM_SOLID_MAT decoration's tiles[0]
   is an OBJ_EVENT_GFX id that sub_80BBDD0 writes into VAR_OBJ_GFX_ID_n
   at RUNTIME, so none of the 45 doll/cushion sheets is any object's
   graphicsId. Ids 143..188 came out missing and a placed doll rendered
   as nothing. collectGraphicsIds now also takes the decoration catalog
   (parsed before the sprites for that reason) and pulls in every
   SOLID_MAT gfx id.

   A second bug underneath it: parseGraphicsInfo's frame walk keeps
   accepting pic-table entries while the byte size matches, and every doll
   is 16x16/128 in one contiguous run -- so ow_142 was coming out as a
   32-frame sheet made of its neighbours. The graphics info's `inanimate`
   bit (bit 6 of byte 0x0C) now clamps those to a single frame.
   Cache contract ruby51 -> ruby52.

12. THE GLITTER SPARKLE was drawing in the wrong place, and three effects
   that should be invisible were drawing at all. drawFieldEffects renders
   FLDEFF_SPARKLE at fx.x / fx.y -- the field effect ARGUMENTS -- but the
   glitter mat was only carrying its tile in gx/gy, so the sparkle landed
   wherever the previous effect's arguments happened to point. It now sets
   x/y as well.
   Worse, the balloon, breakable door and music note mats were riding the
   field-effect list under FLDEFF_SPARKLE purely to get ticked, so each of
   them painted a stray sparkle. In the ROM all three are tasks with no
   sprite of their own -- the visible part is the metatile they swap or
   the sound they play -- so they now use FLDEFF_SECRET_BASE_TIMER, an id
   nothing draws.

13. THE JUMP MAT LOOKED INERT after the latch fix. drawPlayer arcs the
   sprite by 8 * sin(walkProgress * pi), and walkProgress is derived from
   walkCooldown against walkDuration. The mat's own early return in
   walkHeld (the preventStep equivalent) skips the block that normally
   ticks walkCooldown, so with only `hopping` set the arc evaluated to
   zero every frame -- the sound played and the latch worked, but nothing
   moved. beginMatJump now starts that clock and stepSecretBaseMat ticks
   it, one GetJumpInPlaceMovementAction per beat.
   Worth noting the tests did not catch this: they asserted the SE, the
   two beats and the latch, but never that the player visibly moved. They
   now check walkProgress sweeps the arc.

WHAT IS STILL NOT HERE, AND CANNOT BE

Record mixing. It is the GBA link cable, so a second secret base record
cannot arrive. Specials 16, 17 and 25 are ported and correct but only
ever see slot 0; the registry has nothing to list; and your own base's
owner object stays hidden behind FLAG_DECORATION_1, which is what the
cart does too.

FOOTNOTE -- A WIDER BUG THIS UNCOVERED
======================================================================

Item 9's "placed decorations vanish on CONTINUE" was not a secret base
bug at all; it was one symptom of a general ordering fault, and the fix
there was too narrow.

applySave calls enterMap -- which runs the map's ON_LOAD -- and only
afterwards applies the saved mapLayoutId. setMapLayoutIndex rewrites the
whole grid from the layout table, so it wiped every setmetatile ON_LOAD
had just made. overworld.c does the opposite: InitMapFromSavedGame runs
InitMapLayoutData first and RunOnLoadMapScript after, so ON_LOAD always
lands on top of the layout.

The visible case was Lilycove. LilycoveCity_EventScript_SetWailmerMetatiles
(ON_LOAD, gated on FLAG_EVIL_TEAM_ESCAPED_IN_SUBMARINE being unset)
stamps six solid metatiles over the cove at 76..77 / 12..14. After a
CONTINUE those came back as the pristine layout -- open water, collision
0 -- so the Wailmer were gone and the player could surf to the Aqua
hideout early. The same write also covers the hideout entrance metatiles
just above.

Simply moving setMapLayoutIndex before enterMap does not work: enterMap
opens with restoreMapLayout for a layoutSwapped map, which throws the
saved layout away again and breaks Route 131's post-game Sky Pillar
island. applySave now applies the saved layout after enterMap as before
and then re-runs ON_LOAD, which is the order hardware ends up in. ON_LOAD
scripts are setmetatile writes and are safe to repeat.

Covered by ruby_save: a fixture map whose ON_LOAD stamps a solid metatile
must still be solid, and unwalkable, after CONTINUE.
