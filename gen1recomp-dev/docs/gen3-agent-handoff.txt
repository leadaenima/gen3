4. HARD RULES (NEVER DROP)
--------------------------
- Special id = specials.inc **def_special line minus 11**
  (Heal is line 11 = 0). Confirm with check_specials.py.
- Lua **0 is truthy**. Never `if n then` for C `if (n)`.
  Use `n ~= 0` / `dx == nil`.
- `runSpecial` must **return** values that `specialvar` stores.
  Setting VAR_RESULT is optional if you return.
- Specials that return **0 as a valid value** must `return` from the
  elseif. The footer is `if after ~= before then return after else
  return 0` and will eat a legitimate 0 that was already 0.
- MapGrid includes **MAP_OFFSET 7**. Collision bits 10–11 = 0x0C00.
- Cached IR still nops newly decoded opcodes until the player
  re-imports the ROM. No cache bump unless extractor/IR must change.
- `mapMatches` is permissive on non-`gN_M` ids. Rusturf tests must
  use `id = "g24_4"`.
- Do **not** call `setupMauvilleOldMan()` from `Game3.new()`.
- Do **not** name an OW helper `Game3:setWeather` (collides with the
  battle setter).
- Waterfall stays climb-only (do not force south).
- `Game3.new()` does **not** always init `scriptVars`. Tests must
  `g:setScriptVar(...)` not raw `g.scriptVars[x] =` on a fresh instance.
- `runSpecial` is huge. New branches should `return self:foo()` with
  **no extra locals** (LuaJIT 200-local limit). Wrap new tests in
  IIFEs `(function() ... end)()`. Require Gen3Script **inside** the
  IIFE; a `local` in an earlier IIFE is not visible later.
- Do not copy Nintendo graphics into git.
- LÖVE does not hot-reload. Tell the player to restart after code
  changes.
- Port as-is. No placeholders. User asked for **bigger slices**, not
  one-house / one-special phases.

How gbaRandom maps to tests:
  Game3:gbaRandom() is (rng(65536) - 1). If `g.rng = function() return 1
  end` then gbaRandom is 0. Infect needs rng to return 0x4001 / 0x8001 /
  0xC001. Spread is `Random() % 3 == 0`, so rng=1 (gbaRandom=0) ALWAYS
  spreads if a mon already has active Pokerus.

PHASE 209 -- MP2K AUDIO EXTRACTOR (done; the player is NOT written yet)
-----------------------------------------------------------------------
src/import/RomExtractorGen3Audio.lua, wired into RomExtractorGen3 as an
eighth stage ("Audio", STAGE_COUNT 7 -> 8) writing data/generated/audio.lua
and assets/generated/audio/mp2k.bin.  Tests: tests/engine/ruby_audio_test.lua.

The shipping decision that matters: everything the player needs --
gSongTable, the song headers, the track byte streams, the voicegroups and
the PCM -- lives in ONE 2.50 MB stretch of cart, 0x42FC88..0x6B0728.  So
the extractor copies that stretch verbatim into mp2k.bin and records
`base`.  It does NOT repack.  Repacking would mean rewriting every
GOTO/PATT/REPT target inside the track streams; instead the player walks
exactly the structures the GBA walks and turns a ROM pointer into a blob
index with `offset - base`.  Verified: all 416 live song headers resolve
inside the blob and the bytes are identical to the cart.

Measured against the US 1.0 cart:
  468 song table entries, of which 416 carry a real SongHeader and 52
    share dummy_song_header (trackCount 0 -- that is how they are told
    apart; readSongHeader rejects them)
  114 voicegroups reached, including the ones key-split (type 0x40) and
    rhythm (type 0x80) voices nest
  128 DirectSound samples, 0.44 MB of signed 8-bit PCM
  music player index: 57 songs on player 0 (BGM), 201 on 1, 103 on 2, 7 on 3

The track command decoder (Audio.commandLength) is the part to trust and
not re-derive.  0x00..0x7F are argument bytes; a bare argument byte means
running status (repeat the previous opcode).  0x80..0xB0 are waits.  0xB1
FINE ends a track.  0xB2 GOTO / 0xB3 PATT carry a u32 address, 0xB5 REPT a
count then a u32.  0xB9 MEMACC takes 3, 0xCD XCMD takes 2, the 0xBA..0xC8
band takes 1.  0xCE EOT, 0xCF TIE and the 0xD0..0xFF notes are VARIABLE:
they eat argument bytes only while those bytes stay below 0x80 (max 1, 2
and 3 respectively).  Getting a length wrong desyncs the stream silently,
so it was checked structurally: MUS_TITLE's ten tracks walk end to end and
tile exactly (track 1 0x68368C..0x683A37, track 2 starts at 0x683A37, ...),
and track 10 ends at 0x686463 -- one byte before the song header at
0x686464.  A wrong length cannot produce that.

Structures (include/gba/m4a_internal.h):
  struct Song       8  { SongHeader*, u16 ms (music player), u16 me }
  struct SongHeader    { u8 trackCount, u8 blockCount, u8 priority,
                         u8 reverb, ToneData* tone, u8* part[trackCount] }
  struct ToneData  12  { u8 type, u8 key, u8 length, u8 pan_sweep,
                         WaveData* wav, u8 attack/decay/sustain/release }
  struct WaveData  16 + PCM { u16 type, u16 status, u32 freq, u32 loopStart,
                         u32 size, s8 data[size] }
  ToneData.type: low 3 bits pick the channel kind (0 DirectSound,
  1/2 square, 3 programmable wave, 4 noise), 0x08 FIX, 0x40 key split,
  0x80 rhythm.  For splits and rhythm, `wav` is another voicegroup.
  WaveData.freq is the middle-C rate << 10 (e.g. 3344 Hz for one title voice).


PHASE 210 -- MP2K PLAYER (music plays)
---------------------------------------
src/core/Mp2kSynth.lua (sequencer + mixer) and src/core/Mp2kAudio.lua
(playback), hooked into Game3, Game3Boot and Gen3Script.
Tests: tests/engine/ruby_mp2k_player_test.lua.

Mp2kSynth copies ChipSynth's INTERFACE on purpose -- newEngine,
sampleStereo, finished, soundData -- so the buffer plumbing reads the same
either side.  Nothing else is shared; ChipSynth interprets Game Boy channel
programs and MP2K shares neither the command set nor the timing model.
Mp2kAudio renders on the MAIN THREAD, unlike ChipAudio's chip_worker: the
engine runs ~10x realtime and a frame needs only ~740 samples, so buffers
are 2048 (not 8192) to keep the initial fill off the frame budget.

Timing, all confirmed against the cart:
  - tempoD = 2 * the TEMPO byte.  Each frame tempoC += tempoD*tempoU/256,
    and every 150 units is one tick; 24 ticks per quarter note.  The four
    songs sampled decode to 144 / 108 / 196 / 154 BPM, which are musically
    sensible and distinct -- a broken tempo decode would not do that.
  - the frame rate is the GBA's 59.7275 Hz vblank, not a round 60.
  - gClockTable: 0..24, then 28,30,32,36,40,42,44,48,52,54,56,60,64,66,68,
    72,76,78,80,84,88,90,92,96.  Waits 0x80+n index it directly, notes
    0xD0+n at n+1, and 0xCF TIE holds until an EOT.

TWO BUGS WORTH NOT REINTRODUCING:
  1. RUNNING STATUS ONLY LATCHES FOR COMMANDS >= 0xBD.  Waits and the
     flow-control commands below that must NOT latch.  When they did, the
     argument bytes after a wait were read as another wait, the pointer
     never advanced and every track wedged: the title theme played 38 notes
     in 12 seconds and then went silent.  With it fixed, 743.
  2. THE GAME BOY ENVELOPE IS COUNTER-BASED ON A 0..15 LEVEL, and a rate of
     0 means the step is INSTANT, not "one level per frame".  Ruby's flat
     organ-like voices are written as attack 0 / release 0 (see the title
     voicegroup: 0/7/15/0), so treating 0 as a slow ramp faded them in over
     a quarter second.  DirectSound is the different, 0..255 scheme:
     attack adds, decay and release multiply by n/256, sustain holds.

DirectSound pitch: rate = (WaveData.freq/1024) * 2^((key-60)/12), honouring
loopStart/size, 12 channels with stealing.  A voice with TONE_FIX (0x08)
ignores the key and plays at a constant rate.  Rhythm voices (0x80) index
their sub-voicegroup by the played key and their own `key` field replaces
the pitch, so EOT has to match on the key the TRACK wrote -- kept as
ch.noteKey -- not the one the drum sample plays at.

Hooks now live:
  - map BGM from the header's `music` on enterMap.  0 is MUS_NONE (stop);
    0x7FFF marks the maps whose theme depends on where you stand (desert,
    underwater) and keeps whatever is playing.  Re-entering a map that
    shares its song does not retrigger it.
  - battle themes via the registry's named ids (vsWild / vsTrainer), and
    endBattle restores the map theme from the header.
  - boot: openIntro plays MUS_INTRO, openTitle MUS_TITLE; the copyright
    screen stays silent and the main menu keeps the title theme running.
  - script ops playbgm / savebgm / fadedefaultbgm now dispatch, and
    0x36 fadenewbgm / 0x37 fadeoutbgm / 0x38 fadeinbgm are DECODED for the
    first time (they used to size correctly but fall through to nop).
  - Game3:updateMusic runs the pump at a fixed 60 Hz and is called before
    update's boot-phase early return, so the cinematic has music too.


PHASE 211 -- SOUND EFFECTS, FANFARES AND CRIES (ruby30)
--------------------------------------------------------
Mp2kAudio now holds FOUR independent voices -- bgm, se, fanfare, cry --
each with its own engine and QueueableSource.  This is not a design
choice, it is what Ruby does: an effect is an ordinary song in the same
gSongTable, distinguished only by the music player in the table's second
field.  Player 0 is BGM, players 1..3 are effects.  So playse and
playfanfare take a song id exactly like playbgm and differ only in which
voice they land on and whether loops are allowed.

Effects build with allowLoops = false, which matters: a jingle's trailing
GOTO would otherwise repeat it forever.  Measured against the cart, every
player-1/2 song then ends on its own with a sensible length -- SE_WIN_OPEN
0.39s, SE_DOOR 0.57s, SE_SAVE 1.74s, MUS_HEAL 2.29s, MUS_OBTAIN_ITEM
2.43s -- while player-0 songs keep looping, which is the correct split.

A live fanfare MUTES bgm underneath (not pauses), so the music resumes
where it would have been rather than where it stopped.  Close enough to
the ROM to not be worth the bookkeeping, but it is a real difference.

BUG FIXED HERE, and it is the reason two songs never reported finished:
a track stopped by anything other than FINE -- a GOTO with loops
disabled, or an unknown opcode -- did NOT release the notes it was
holding.  The sustaining channel then kept the engine alive forever.
Engine:stopTrack now does both, and finished() also checks the CGB
channels, which it did not before.

CRIES.  gCryTable 0x452590 and gCryTable2 0x4537C0, 388 ToneData each
(decomp: sound/voice_groups.inc:12136 and :12527).  They are reachable
only from code, never from a song header, so Audio.scanCries pulls their
samples into the shipped span explicitly -- the span itself did not move,
they were already inside it, but the sample count went 128 -> 516.

  - Every entry is the `cry` macro verbatim: type 0x20, key 60, ADSR
    255/0/255/0.  That is what validates the offset, and a wrong one
    fails loudly at import instead of going silent at runtime.
  - 0x20 IS NOT THE FIXED-FREQUENCY BIT.  That is 0x08, on its own.  The
    old test `typ >= TONE_FIX and typ < TONE_SPLIT` called every cry
    fixed; harmless by luck (cries are recorded at key 60, so both paths
    give the same rate) but wrong for any 0x28 voice.
  - Species -> cry id is resolved AT IMPORT into audio.cries[1..411], so
    the runtime only does cryTable + cries[species]*12.  PlayCryInternal
    decrements the species before SpeciesToCryId, so all the bounds are
    on the 0-based index: below 251 the id is the index itself, 251..275
    are the unused `?` slots and all borrow Unown's 200, and from 276 it
    reads gSpeciesIdToCryId at 0x1FDE6A because the Hoenn cries were
    recorded in a different order than the species were numbered
    (Treecko is species 277 but cry 273).  Species 411 lands exactly on
    entry 387, the last of the 388 -- which is the check that the whole
    mapping is right.
  - A hole anywhere in cries[] would serialize as a truncated array and
    silently lose every species past it, so one bad lookup drops the set
    and the Gen 1/2 fallback takes over.

Mp2kSynth.newCryEngine does NOT rebuild the PokemonCrySong template.  It
points a bare engine's voicegroup straight at the cry's ToneData and
strikes middle C, which is all the template amounts to.  Its one track
is created already stopped -- there is no byte stream to sequence, the
track exists only to carry the volume and pan the mixer reads.  The
sample does not loop, so the channel dies at its end and the engine
reports finished with nothing timing it.  Rendered against the cart:
Bulbasaur 0.79s, Mewtwo 1.44s, Mudkip 0.35s, all ending by themselves.

VOLUME.  Ruby's OPTION screen has no volume rows, because the ROM has

SCRIPT OPCODES.  0x2F..0x38 is one contiguous sound block: playse,

PHASE 213 -- FONT 4, THE PARTY MENU'S SMALL TEXT (ruby32)  DONE
------------------------------------------------------
Level and HP numbers were drawn with FONT3 (8x16) and bled a row below
their box; the nickname was oversized for the same reason.  All three now
use font 4.  Notes below are the reasoning, kept because the indexing is
genuinely non-obvious and cost an hour.

gWindowTemplate_81E6CAC (text.c) selects font 4, and the nickname, level
and HP all share that template.  In sFonts, latin font 4 is slot 11:
  { 1, (u8 *)gFont4LatinGlyphs, 32, 0 }   // type 1, glyphSize 32
Slot 11 and 12 share the pointer; slot 12 is the same pool drawn type 2.

DO NOT index that pool by character code.  Rendering it directly puts
lowercase at the digit codes -- an hour was lost to this.  Type 1 goes
through a lookup (GetGlyphTilePointers case 1):
  upper = glyphs + sFontType1Map[2 * glyph]     * 32
  lower = glyphs + sFontType1Map[2 * glyph + 1] * 32
so each character names TWO 8x8 tiles out of a shared pool, and the pool
is not charmap-ordered.  A content scan of the whole cart for a
charmap-ordered 8x8 font finds only noise, which is the symptom of this.

sFontType1Map is a u8[] of 512 bytes, src/data/text/type1_map.h, and it
starts distinctively -- that is the search signature:
  D4 D4  D4 31  D4 32  D4 33  D4 34  D4 35  D4 36  D4 37  D4 38  D4 39
Tile 0xD4 is the blank.  Note every one of those upper entries is 0xD4:
for most characters the upper tile is EMPTY and the whole letter sits in
the lower tile.  That is precisely why PartyMenuDoPrintLevel copies only
0x80 bytes from gTileBufferPtr + 0x100 (the window's lower tile row, 4
tiles) and PartyMenuDoPrintHP copies 0x100 (8 tiles): the numbers are 8
pixels tall.  The nickname copies 0x200 from +0, both rows, so nicknames
really are 16 tall and already render correctly.

Widths come from sFont4Widths indexed by the LOWER tile, not by the
character (text.c GetGlyphWidth):
  width = sFont4Widths[sFontType1Map[2 * glyph + 1]]

Known offsets already in hand:
  sFonts               0x1E6B30  (RomExtractorGen3.findFontTable finds it)
  gFont3LatinGlyphs    0xEA2C44  (slot 10, already extracted)
  gFont4LatinGlyphs    0xEA6BC4  (slot 11 -- the POOL, not charmap order)
